# Migrating to Ryder v0.3.0

v0.3.0 is the first Ryder release with breaking changes. There are four, and
this document tells you what each one does, how to tell whether it affects you,
and exactly what to change.

Every step here was executed against a real consumer site before being written
down. Where a result is stated as fact, it was measured.

## Before you start

**Upgrade one release at a time.** Ryder is consumed as a pinned submodule, so
nothing moves until you move it. Go `v0.2.3 → v0.2.4 → v0.2.5 → v0.3.0`,
building and looking at the site between each. Jumping straight here bundles
four breaking changes with roughly twenty-five behaviour changes, and if
something shifts you will not know which one caused it.

**Audit your overrides first — this matters more than any individual item.**
Hugo template overrides do not conflict. A file at
`layouts/partials/head/schema.html` in your site wins over the theme's version
**silently, forever** — no warning, no merge marker, no signal the theme's copy
moved on. The most likely outcome of this upgrade is not breakage; it is
upgrading, seeing green, and receiving none of the fixes because you override
the files that got fixed.

```bash
cd layouts && find . -type f | while read -r f; do
  [ -f "../themes/ryder/layouts/$f" ] && echo "$f"
done
```

For each hit: delete it (the theme now does the job), rebase your changes onto
the theme's new version, or keep it deliberately and write down why. Anything
you keep is a fix you are opting out of — fine, but make it a decision.

**Capture a baseline** so you can prove what changed:

```bash
hugo --minify -d /tmp/before
```

Extended Hugo is required (`hugo version` must contain `+extended`).

## Breaking change 1 — the `*-tw` npm scripts are gone

**Breaks build commands, not rendering.** This is the one most likely to bite,
because it fails in CI rather than locally.

`build-tw`, `watch-tw`, and `deploy-tw` have been deleted. They ran the Tailwind
CLI to produce a committed `assets/css/style.css` that no template ever read —
Tailwind already compiles *inside* the Hugo build, via `head/css.html`'s
`css.PostCSS` plus `postcss.config.js`.

**Affects you if** any build command, `vercel.json`, Netlify config, GitHub
Action, or documented dev loop mentions `build-tw` / `deploy-tw` / `watch-tw`.

**Do this:**

1. Confirm your build works with `hugo --minify` alone.
2. Ensure `tailwindcss`, `postcss`, `postcss-cli`, and `autoprefixer` are at your
   project root, with a `postcss.config.js`.
3. Remove the script from every build command and from your docs.

> **Pin Tailwind to v3.** A bare `npm i -D tailwindcss` installs v4 today, and v4
> cannot be a PostCSS plugin directly — its plugin moved to
> `@tailwindcss/postcss`, and `hugo --minify` fails outright. Ryder is a v3
> theme. Install `tailwindcss@^3.4.0` explicitly.

There is **no separate CSS build step** and no two-terminal dev loop. `hugo
server` alone suffices. If your notes say otherwise, they were describing the
scripts this release deleted.

You also inherit the deletion of `assets/css/style.css` itself. If anything
resolves that path by hand, remove it.

## Breaking change 2 — PostHog no longer widens `script-src`

**Fails in the visitor's browser, not in your build.** CSP violations do not
break builds; they break pages, silently, after deploy.

Previously `posthog.html` inlined its bootstrap snippet, so `csp.html` appended
`'unsafe-inline'` to `script-src` for *every* PostHog site — giving away the
CSP's most valuable directive by default. The snippet is now built with
`resources.FromString | js.Build | fingerprint` and loaded via `src` +
`integrity`, so the widening is gone.

**Affects you if** your site has any inline `<script>` of its own. Find them:

```bash
grep -rn '<script' layouts/ | grep -v 'src='
```

**Do this** — pick one per script:

- **Preferred:** add its hash to the new `params.csp.scriptSrcHashes`. Compute it
  from the *rendered* output, not the template:

  ```bash
  # after a production build, for each inline script body
  printf '%s' "$SCRIPT_BODY" | openssl dgst -sha256 -binary | openssl base64
  ```

  ```toml
  [params.csp]
    scriptSrcHashes = ["sha256-…"]
  ```

- Or move the script into `assets/js/extended.js`, the theme's sanctioned
  custom-JS hook, which is bundled and needs no hash.
- Or set `params.csp.scriptSrc = "'unsafe-inline'"` explicitly. The point of this
  change is that widening becomes a decision rather than a default.

**Verify with a production build and a browser console showing zero CSP
violations — not by reading the config.** `hugo server` will not tell you: the
dev environment does not gate analytics the same way.

> Note: browsers correctly ignore `frame-ancestors` in a `<meta>`-delivered CSP,
> so you may see a console notice about it. That is pre-existing and inert, not
> a symptom of this change.

## Breaking change 3 — JSON-LD output changes shape

`head/schema.html` has been rebuilt to construct Hugo `dict`s and `jsonify` them
instead of hand-writing JSON strings. This eliminates a whole bug class
structurally: the previous version emitted JavaScript comments *inside*
`<script type="application/ld+json">`, so every affected block failed to parse
and was discarded wholesale.

**If you override `head/schema.html`, this is your cue to stop.** Overriding it
silently drops every block the theme emits — WebPage, BlogPosting, the site-wide
entity, BreadcrumbList — with no build error and correct-looking HTML.

**Do this instead:**

1. Delete your override.
2. Set the site-wide entity type if it is not an Organization:
   ```toml
   [params.schema]
     type = "MusicGroup"   # or Person, LocalBusiness, …
   ```
3. Put anything the theme does not model into the new
   `layouts/partials/head/schema-extra.html`, which is called from
   `head-seo.html` and shadows cleanly. The theme's blocks still render.

   ```go-html-template
   {{ if .IsHome }}
     {{ $album := dict
          "@context" "https://schema.org"
          "@type" "MusicAlbum"
          "name" "Album Title"
          "byArtist" (dict "@type" "MusicGroup" "name" site.Title)
     }}
     <script type="application/ld+json">{{ $album | jsonify | safeJS }}</script>
   {{ end }}
   ```

> **`| safeJS` is required and easy to forget.** Without it, Go's contextual
> escaping treats `<script>` as a JS context and emits your JSON as a *quoted
> string* — which parses as a string, not an object, and is silently useless as
> structured data. Build a dict and pipe through `jsonify | safeJS`; never
> hand-write JSON.

**Measured result on a real site** that overrode `head/schema.html` to emit
`MusicGroup` + `MusicAlbum`: after deleting the override, setting
`schema.type = "MusicGroup"`, and porting the album block into
`schema-extra.html`, the home page emitted **WebPage + MusicGroup + MusicAlbum**
(all valid), and interior pages regained **BlogPosting + BreadcrumbList** that
the override had been silently suppressing. Strictly more structured data, one
fewer file.

Revalidate at Google's Rich Results Test afterward. Practical risk is low — the
old output never parsed — but verify rather than assume.

## Breaking change 4 — the Tailwind config is now a preset

`tailwind.config.js` was a *site* config: its `content` array globbed
`./exampleSite/…` and `./themes/ryder/layouts/**/*.html`, none of which resolves
from a consumer's project root.

The theme now ships `tailwind.preset.js` carrying only `theme`, `darkMode`, and
`plugins` — no `content`.

**Affects you if** your `tailwind.config.js` does
`require('./themes/ryder/tailwind.config.js')`.

**Do this:**

```js
module.exports = {
  presets: [require('./themes/ryder/tailwind.preset.js')],
  content: [
    './themes/ryder/layouts/**/*.html',
    './layouts/**/*.html',
    './content/**/*.md',
    './hugo_stats.json',
  ],
};
```

This one fails loudly and immediately at build time, so it is the least
dangerous of the four.

## Not a breaking change, but do not skip it: `[outputs]`

Earlier guidance said the theme's `[outputs]` block is inherited by consumers
and that you could delete yours. **That is false**, and following it would have
silently removed `llms.txt` from your site.

Measured on a clean consumer whose entire config was `baseURL`, `title`,
`theme`, and `themesDir`:

| Consumer config | `home` outputs | `/llms.txt` |
|---|---|---|
| no `[outputs]` | `['html', 'rss']` (Hugo's default) | **not written** |
| `home = ["HTML", "RSS", "LLMSTxt"]` | as written | written |

`outputFormats` **is** inherited — the `LLMSTxt` format definition comes from the
theme in both cases — but `outputs` is not. That is why the block you need is
one line and not a format redefinition.

**Keep or add this to your own config:**

```toml
[outputs]
  home = ["HTML", "RSS", "LLMSTxt"]
```

The same caveat applies to `[build]`: it is **not** inherited either. If you do
not have a `[build] writeStats = true` block plus cachebusters in your own
config, add one — without it Tailwind falls back to scanning `layouts/**/*.html`
and any dynamically-assembled class is silently purged from your CSS.

## Verify

```bash
hugo --minify -d /tmp/after
diff -rq /tmp/before /tmp/after
```

Then confirm each of these, rather than eyeballing the site:

1. **Every JSON-LD block parses.** Extract each
   `<script type="application/ld+json">` body and run it through a JSON parser.
   Note that minified output drops attribute quotes, so match loosely.
2. **`script-src` contains no `'unsafe-inline'`** unless you put it there
   deliberately, and every inline script you kept has a matching hash.
3. **Zero CSP violations** in a browser console against a *production* build.
4. **`llms.txt` and `index.xml` are still written.**
5. **Your CSS still contains dynamically-assembled classes**, if you rely on any.
6. Build with your CI's exact command, not just `hugo`.

## Rollback

```bash
git -C themes/ryder checkout v0.2.5
git add themes/ryder && git commit -m "Roll back Ryder to v0.2.5"
```

Config additions from this guide are inert on v0.2.5 except
`params.csp.scriptSrcHashes`, which is simply ignored there — so a rollback needs
`params.csp.scriptSrc` restored if you had removed it.
